---

## 1. Нормативные слова

| Термин | Значение |
| --- | --- |
| **ОБЯЗАН / MUST** | безусловное требование |
| **НЕ ДОЛЖЕН / MUST NOT** | безусловный запрет |
| **СЛЕДУЕТ / SHOULD** | предпочтительное требование; отклонение требует обоснования |
| **МОЖЕТ / MAY** | допустимая опция |

---

## 2. Формат требования

Каждое значимое требование получает стабильный идентификатор и документируется единообразно:

```yaml
requirement:
  id: REQ-DOMAIN-NNN
  statement: >
    Краткое и проверяемое нормативное требование.
  rationale: >
    Почему требование существует.
  verification_method:
    - inspection
    - schema_test
    - static_validation
    - unit_test
    - integration_test
    - replay_test
    - mutation_test
  acceptance_criteria: []
  related_objects: []
  related_documents: []
  status: SPECIFIED
```

---

## 3. Соглашения об идентификаторах

Формат ID требования:

```text
REQ-<DOMAIN>-<NUMBER>
```

Примеры доменов: `DATA`, `RULE`, `VALIDATION`, `RISK`, `AI`, `EXEC`, `PORTFOLIO`, `OUTPUT`, `EVIDENCE`, `GOV`.

Идентификатор уникален, стабилен, не меняется при переименовании, не зависит от файла и используется в документации, схемах, тестах и логах.

---

## 4. Жизненный цикл статуса требования

```text
DRAFT → REVIEWED → SPECIFIED → VERIFIED → DEPRECATED
```

Статус `VERIFIED` присваивается только при наличии реально исполняющейся проверки, покрывающей `acceptance_criteria`. Требование НЕ ДОЛЖНО помечаться `VERIFIED` на основании существования кода проверки без её исполнения (ср. `REQ-EVIDENCE-001`).

---

## 5. Сквозные требования (seed set)

Ниже — фундаментальные требования, применимые ко всей системе. Раздел 5.1 закрепляет положения, уже присутствующие в мастер-ТЗ. Раздел 5.2 добавляет шесть требований, выведенных из post-mortem TradAlert; они закрывают зазор между «болезнь описана прозой» и «в CI есть проверка, которая её ловит».

Доменные требования (по конкретным rules, strategies, features) появляются по мере формализации уроков и здесь не перечисляются.

### 5.1. Закреплено из мастер-ТЗ

```yaml
requirement:
  id: REQ-DATA-002
  statement: >
    Отсутствующий или устаревший критический вход НЕ ДОЛЖЕН молчаливо
    становиться нулём или нейтральным значением. Он ОБЯЗАН порождать
    UNKNOWN; для live-входа критический UNKNOWN ОБЯЗАН приводить к NO_TRADE.
  rationale: >
    Молчаливая подстановка нуля превращает «нет данных» в ложно-уверенное
    значение и снимает предохранитель ровно там, где он нужен.
  verification_method: [unit_test, integration_test]
  acceptance_criteria:
    - отсутствующий вход в тесте даёт UNKNOWN, а не 0;
    - критический UNKNOWN на live-пути даёт NO_TRADE.
  related_documents: [master_specification/v1.0]     # §15.4, §54.28
  status: SPECIFIED

requirement:
  id: REQ-AI-001
  statement: >
    Вывод AI-агента НЕ ДОЛЖЕН обходить независимый Risk Engine.
    Veto Risk Engine НЕ ДОЛЖЕН отменяться агентом.
  rationale: >
    Право исполнения и право анализа разделены. Агент выбирает допустимое
    действие; допустимость определяет детерминированный Risk Engine.
  verification_method: [integration_test, inspection]
  acceptance_criteria:
    - в тестовом сценарии veto Risk Engine отменяет действие агента;
    - отсутствует путь, которым вывод агента достигает брокера, минуя Risk Gate.
  related_documents: [master_specification/v1.0]     # §30, §32, §38.2
  status: SPECIFIED

requirement:
  id: REQ-AI-002
  statement: >
    AI-агент НЕ ДОЛЖЕН генерировать числовые величины (win rate, вероятность,
    expectancy, score, stop, target, размер позиции, веса, slippage, edge)
    из текста. Такие величины ОБЯЗАНЫ поступать из детерминированных движков
    или из validated expectation estimate.
  rationale: >
    Языковая модель убедительно производит правдоподобные числа. Число без
    статистического источника — это иллюзия точности.
  verification_method: [integration_test, schema_test]
  acceptance_criteria:
    - числовые поля решения заполняются из детерминированных источников;
    - вывод агента с самостоятельно порождённым числом не проходит валидацию.
  related_documents: [master_specification/v1.0]     # §32.5, §54.2
  status: SPECIFIED
```

### 5.2. Выведено из post-mortem TradAlert

```yaml
requirement:
  id: REQ-VALIDATION-001
  statement: >
    Каждый gate, veto или eligibility-фильтр ОБЯЗАН иметь пару входных
    наборов, дающих различный итоговый вердикт. Объект, вердикт которого
    инвариантен ко всем входам, НЕ ДОЛЖЕН допускаться в runtime.
  rationale: >
    Гейт, который не может изменить исход, — не гейт, а декорация. В TradAlert
    R:R-гейт был `if is_long: return True` и проходил семь аудитов, потому что
    это валидная функция с валидными ссылками. Прозаическое описание правила
    этого не ловит; ловит только исполняемый тест на паре входов (mutation).
  verification_method: [mutation_test, unit_test]
  acceptance_criteria:
    - для каждого gate/veto в тестовом корпусе зарегистрирована пара (A, B) с различным вердиктом;
    - принудительная инверсия любого гейта меняет ≥1 вердикт в корпусе; иначе сборка падает.
  related_documents: [master_specification/v1.0]     # §38.2 (расширение перечня инвариантов)
  status: SPECIFIED

requirement:
  id: REQ-VALIDATION-002
  statement: >
    Для тождественного бара и тождественного версионированного конфига
    backtest-путь и live-путь ОБЯЗАНЫ порождать идентичный Decision.
    Расхождение ОБЯЗАНО приводить к провалу сборки.
  rationale: >
    Детерминизма каждого пути по отдельности недостаточно: два пути могут быть
    детерминированы и при этом различны. В TradAlert «текущая дата» на live
    бралась из системных часов, а в backtest — из даты бара, из-за чего пути
    отбирали разные популяции сделок, а метрика edge описывала программу,
    которая не могла взять реально сработавшую сделку. Тождество проверяется
    только сравнением трасс, а не декларацией «используется один объект».
  verification_method: [replay_test, integration_test]
  acceptance_criteria:
    - ночной прогон по эталонному корпусу сравнивает Decision двух путей побитово;
    - любое расхождение → red build;
    - единственные «часы» ниже слоя представления — дата бара, не системное время.
  related_documents: [master_specification/v1.0]     # §37.1 (усиление), §38.2, §54.19
  status: SPECIFIED

requirement:
  id: REQ-DATA-001
  statement: >
    Календарь событий (макро- и корпоративных) ОБЯЗАН быть point-in-time
    датасетом с той же битемпоральной семантикой (event_time и known_from),
    что и рыночные данные. Ни одна дата события НЕ ДОЛЖНА присутствовать
    литералом в исполняемом коде; каждая запись ОБЯЗАНА нести source_id и
    время, с которого она стала известна.
  rationale: >
    Дата, вписанная руками, не проверяема и расходится с реальностью молча.
    В TradAlert календарь давал три разных ответа на один факт из трёх
    источников без провенанса, а даты выводились из несуществующего правила.
    Календарь — единственный класс данных, где обычно забывают применить
    PIT-дисциплину, и он же чаще всего ломается.
  verification_method: [static_validation, schema_test, replay_test]
  acceptance_criteria:
    - статический скан кодовой базы находит ноль литералов дат вне тестовых фикстур;
    - каждая запись календаря имеет source_id, known_from, checksum;
    - регрессионная сверка live-загрузки с эталоном для прошлых дат; расхождение → провал.
  related_documents: [master_specification/v1.0]     # §12 (распространение PIT на календарь), §54.10
  status: SPECIFIED

requirement:
  id: REQ-OUTPUT-001
  statement: >
    Каждое числовое значение в выводе решения (вероятность, ожидание, размер
    выборки, score) ОБЯЗАНО нести идентификатор своего источника — версию
    оценки, ключ когорты (cohort key) или ссылку на модель. Значение без
    провенанса НЕ ДОЛЖНО отображаться.
  rationale: >
    Смещённое число опаснее выдуманного, потому что выглядит обоснованным.
    В TradAlert размер выборки брался из общей fallback-когорты и печатался
    так, будто относился к конкретному узкому случаю; сам поиск когорты
    возвращал ключ, но его выбрасывали при отрисовке.
  verification_method: [schema_test, unit_test]
  acceptance_criteria:
    - schema решения требует поле provenance у каждого числового поля;
    - вывод без провенанса не проходит валидацию.
  related_documents: [master_specification/v1.0]     # §32.5, §34, §31.1
  status: SPECIFIED

requirement:
  id: REQ-EVIDENCE-001
  statement: >
    Присвоение объекту validation stage (V3–V9) ОБЯЗАНО ссылаться на прогон
    валидации, реально исполнившийся в автоматизированном конвейере. Наличие
    реализованной функции валидации само по себе НЕ ДОЛЖНО служить основанием
    для присвоения стадии.
  rationale: >
    Реализованная, но никогда не вызываемая валидация — иллюзия строгости.
    В TradAlert методы deflated Sharpe и White's Reality Check были корректно
    реализованы, но вызывались только вручную из отдельного скрипта; отчёт
    backtest не нёс ни одной из этих метрик.
  verification_method: [inspection, integration_test]
  acceptance_criteria:
    - каждый объект со стадией ≥ V3 ссылается на Validation Run с checksum и run_manifest;
    - отчёт прогона содержит фактические метрики, а не заглушку.
  related_documents: [master_specification/v1.0]     # §24 (усиление увязки), §26
  status: SPECIFIED

requirement:
  id: REQ-RISK-001
  statement: >
    Любой риск-контроль (veto, gate, лимит) в состоянии enabled: false ОБЯЗАН
    сопровождаться датированной ADR с владельцем и сроком пересмотра. По
    истечении срока без продления сборка ОБЯЗАНА падать.
  rationale: >
    Корректно написанный защитный контроль, выключенный «ради неизменности
    baseline», склонен оставаться выключенным неопределённо долго. В TradAlert
    так были выключены шесть готовых контролей. Статус UNSET этого не
    покрывает — контроль задан, но мёртв. Срок годности превращает молчаливое
    выключение в явное, ограниченное во времени решение.
  verification_method: [static_validation, inspection]
  acceptance_criteria:
    - для каждого enabled:false на риск-контроле существует ADR с полями owner, reason, review_by;
    - CI проверяет review_by и падает при просрочке.
  related_documents: [master_specification/v1.0]     # §14.3 (двойник дисциплины UNSET), §30
  status: SPECIFIED
```

---

## 6. Что ещё предстоит

Этот seed-набор — фундамент, а не полный реестр. По мере формализации уроков добавляются доменные требования: к конкретным features (`REQ-DATA-*`), правилам (`REQ-RULE-*`), стратегиям, ограничениям, исполнению и портфелю. Каждое новое требование следует тому же формату и проходит тот же жизненный цикл статуса.
