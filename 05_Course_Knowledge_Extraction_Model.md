Этот документ определяет **процесс** превращения фрагмента урока в формальный объект. Он строится сейчас, до готовности уроков, намеренно: когда полные версии придут (`UDR-001`), извлечение (Этапы 1–2 мастер-ТЗ) должно быть turnkey, а не проектироваться заново. Форма готова — наполнение станет механическим, а не творческим.

---

## 1. Конвейер преобразования

Каждое утверждение урока проходит фиксированную последовательность. Ни один этап не пропускается.

```text
Course Statement
  → Classified Concept          (присвоить класс извлечения)
  → Formal Definition           (точное нейтральное определение)
  → Rule / Event / State / Hypothesis   (определить тип объекта)
  → Machine-Readable Specification       (заполнить схему объекта)
  → Implementation              (позже; вне фазы документации)
  → Validation                  (позже; по протоколу валидации)
  → Approved Runtime Object     (только после validation record)
```

Ключевое правило устава действует на каждом шаге: **утверждение из урока не становится автоматически исполняемым или доказанным.** Переход к `Approved Runtime Object` невозможен без пройденной валидации.

## 2. Классы извлечения

Каждый фрагмент урока получает ровно один класс (перечень зафиксирован в онтологии, §6):

```text
CONCEPT                  DEFINITION               OBSERVATION
FEATURE                  INDICATOR                RULE_CANDIDATE
EVENT_CANDIDATE          STATE_CANDIDATE          SETUP_CANDIDATE
STRATEGY_CANDIDATE       RISK_POLICY              EXECUTION_POLICY
HYPOTHESIS               EXPECTATION_CLAIM        LIMITATION
WARNING                  EDUCATIONAL_EXPLANATION  NON_EXECUTABLE_GUIDANCE
```

### Отображение класса в целевой объект и каталог

| Класс извлечения | Целевой тип объекта | Каталог |
| --- | --- | --- |
| `INDICATOR`, `FEATURE` | `feature` / `indicator` | `features.yaml` |
| `RULE_CANDIDATE` | `rule` | `rules.yaml` |
| `EVENT_CANDIDATE` | `event` | `events.yaml` |
| `STATE_CANDIDATE` | `state` / `state_machine` | `states.yaml` |
| `SETUP_CANDIDATE` | `setup` | `setups.yaml` |
| `STRATEGY_CANDIDATE` | `strategy` | `strategies.yaml` |
| `RISK_POLICY` | `policy` (risk) | `constraints.yaml` / risk-политики |
| `EXECUTION_POLICY` | `policy` (execution) | execution-политики |
| `HYPOTHESIS`, `EXPECTATION_CLAIM` | `hypothesis` / `expectation_definition` | `hypotheses.yaml` / `expectations.yaml` |
| `CONCEPT`, `DEFINITION` | термин | `terms.yaml` (глоссарий) |
| `LIMITATION`, `WARNING` | атрибут объекта | в поле `limitations` соответствующего объекта |
| `EDUCATIONAL_EXPLANATION`, `NON_EXECUTABLE_GUIDANCE` | — | остаётся только пояснением; в код не превращается |

**Не всё содержание урока превращается в код.** Два последних класса — это материал, который поясняет и обучает, но не порождает исполняемого объекта. Попытка формализовать их — источник ложных правил.

## 3. Процедура извлечения одного фрагмента

При обработке каждого фрагмента ОБЯЗАТЕЛЬНО:

1. извлечь концепт;
2. найти скрытые параметры (пороги, периоды, временны́е допущения, спрятанные в прозе);
3. определить нужный тип объекта;
4. дать точное нейтральное определение;
5. сохранить ссылку на модуль урока (`course_module_refs`);
6. указать evidence status (по умолчанию — гипотеза, не факт);
7. не выдавать утверждение за доказанный факт.

### Пример

Фрагмент: «после сильного импульса цена часто делает передышку».

Это **не** готовое правило. Формализация:

```yaml
classification: HYPOTHESIS
formalization_status: UNSET
extracted:
  concept: "консолидация после импульсного движения"
  hidden_parameters:
    - "что считается «сильным импульсом» (порог) — UNSET"
    - "что считается «передышкой» (диапазон/длительность) — UNSET"
    - "окно наблюдения — UNSET"
  candidate_object_type: event_candidate | state_candidate   # уточняется при формализации
  evidence_status: HYPOTHESIS
  course_module_ref: null            # заполняется ссылкой на конкретный урок
  note: >
    «Часто» — не число. Утверждение фиксируется как гипотеза с UNSET-параметрами
    и не превращается в правило до калибровки и валидации.
```

Слова-маркеры, требующие формализации или статуса `UNSET`: сильный, хороший, слабый, близко, красивый, качественный, нормальный, плохой. Каждое такое понятие получает формальное определение со ссылкой на параметры, либо статус `UNSET`, либо признаётся только образовательным описанием.

## 4. Как это включается, когда уроки готовы (Этапы 1–2)

**Этап 1 — Инвентаризация.** Собрать все модули уроков и любой сопутствующий материал в `Source Inventory`.

**Этап 2 — Извлечение.** Из каждого модуля извлечь термины, концепты, observations, indicators, rules, events, states, regimes, setups, triggers, strategies, risk/management/exit-правила, параметры, expectations, claims, warnings, limitations, источники — по процедуре раздела 3, с отображением по таблице раздела 2.

**Этап 3 — Нормализация** (следующий за извлечением, здесь упомянут для полноты цепочки). Найти дубли, синонимы, разные определения одного объекта, одинаковые имена разных объектов, скрытые пороги и временны́е допущения, неполные exit-правила, неформальные состояния, противоречия между модулями.

До готовности уроков (`UDR-001`) Этапы 1–2 не запускаются на реальном материале; настоящий документ фиксирует их метод, чтобы запуск был немедленным.

## 5. Инварианты извлечения

- Один фрагмент → один класс извлечения.
- Каждый извлечённый объект несёт `course_module_refs` (provenance к уроку) и общий блок метаданных.
- Evidence status по умолчанию — `HYPOTHESIS`; повышение стадии — только через evidence framework (`20`) и протокол валидации (`22`).
- Скрытый параметр никогда не «додумывается» до конкретного значения: он фиксируется как `UNSET` в реестре параметров (`10`) со всеми обязательными атрибутами.
- Утверждение с числом-маркером («часто», «обычно») не наделяется числом из «здравого смысла»; число появляется только из исследования.
