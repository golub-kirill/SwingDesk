## 1. Принцип point-in-time

> Система МОЖЕТ использовать только информацию, доступную на момент решения.

Нарушение этого принципа (look-ahead) — самый разрушительный класс ошибки в backtest, потому что он бесшумно завышает результат и не воспроизводится в live. Он объявляется формальным инвариантом:

```text
Future data cannot affect a past decision.
```

Инвариант проверяется исполнением (`REQ-VALIDATION-002`, `34_Test_Strategy`), а не декларацией.

---

## 2. Восемь видов времени

Для каждого значения система ОБЯЗАНА различать:

```text
event_time         — когда событие произошло в реальности
observation_time   — когда значение стало наблюдаемым
publication_time   — когда источник его опубликовал
available_time     — когда оно стало доступно системе
ingestion_time     — когда система его приняла
processing_time    — когда обработка завершилась
decision_time      — когда система приняла решение
execution_time     — когда решение было исполнено
```

**Рабочий пример.** Компания опубликовала отчёт в 16:05; источник передал данные в 16:05:07; система получила их в 16:05:09; обработка завершилась в 16:05:12. Backtest НЕ ДОЛЖЕН использовать эту информацию для решения в 16:05:00 — она стала доступна позже.

Определяющая величина для допустимости — **`available_time`**: решение с `decision_time = T` МОЖЕТ опираться только на значения с `available_time ≤ T`.

## 3. Битемпоральность

Каждый факт живёт на двух временны́х осях одновременно:

```text
event_time / effective_time   — когда факт относится к миру
known_from                    — когда факт стал известен нам
```

Запрос «что было известно на момент `T`» (`as_of(T)`) возвращает только факты с `known_from ≤ T`. Без второй оси невозможно корректно смоделировать пересмотры (revisions), переносы и поздние публикации, а любой backtest, касающийся пересматриваемых данных, заражён look-ahead.

Битемпоральность применяется **ко всем** классам данных, включая календарь событий (см. раздел 6). Календарь — единственный класс, где эту дисциплину обычно забывают, и именно поэтому она вынесена в `REQ-DATA-001`.

## 4. Отсутствующие и устаревшие данные

Отсутствующий или устаревший критический вход НЕ ДОЛЖЕН молчаливо превращаться в ноль или нейтральное значение (`REQ-DATA-002`). Он порождает `UNKNOWN`.

```text
missing / stale critical input
  → UNKNOWN
  → (для live-входа) NO_TRADE
```

Причины `UNKNOWN` перечислены в онтологии (§8): missing data, insufficient history, stale data, unresolved parameter, unsupported market, calculation failure, conflicting source values. Ни одна из них не эквивалентна `FALSE`.

Политики для каждого поля (`missing_value_policy`, `stale_value_policy`) задаются в спецификации поля данных и по умолчанию НЕ ДОЛЖНЫ быть «подставить 0».

## 5. Adjusted и raw цены

Три ряда с несовместимым назначением, которые запрещено молча смешивать:

```text
Raw prices
  — для моделирования исполнения и реальных уровней ордеров

Adjusted prices
  — для некоторых видов исторического анализа (напр., непрерывность на сплитах)

Adjusted total-return series
  — для оценки доходности с дивидендами, когда это уместно
```

> Запрещено незаметно смешивать adjusted signal series и raw execution series.

Практическое следствие: если сигнал считается на adjusted-ряде, а исполнение моделируется на нём же, уровни ордеров будут неверны на инструментах со сплитами/дивидендами. Каждое поле цены несёт явную `adjustment_policy`; сигнальный и исполнительный слои декларируют, какой ряд используют, и рассогласование ловится проверкой качества данных.

## 6. Календарь событий как point-in-time датасет

Календарь макро- и корпоративных событий (заседания регуляторов, публикации статистики, отчётности, сплиты, дивиденды) — это **датасет**, а не константы в коде. К нему применяются все правила выше:

- **Ноль литералов дат в исполняемом коде** (`REQ-DATA-001`). Дата события — это запись с провенансом, полученная фетчером, а не вписанная руками.
- **Каждая запись несёт** `source_id`, `known_from`, `checksum`.
- **Битемпоральность обязательна.** Многие расписания публикуются заранее и помечаются как предварительные до подтверждения; `known_from` и признак `tentative` фиксируют это. Публикатор нередко сам сообщает дату последнего обновления страницы — она и есть `known_from`.
- **Fail-closed.** Если календарь недоступен или устарел сверх допустимого, вход блокируется, а не проходит по устаревшему списку. Выход из позиции при этом не блокируется. Логовое предупреждение не является контролем.
- **Провенанс в выводе.** Если дата события участвует в решении, вывод несёт её источник (`REQ-OUTPUT-001`). Три источника, дающие три ответа без указания, какой использован, — недопустимое состояние.

Полная спецификация поля данных (структура `data_field`), конвейер, манифест датасета и перечень проверок качества — в `07_Data_Pipeline_and_Data_Contracts.md`.

## 7. US и Canada

Документация ОБЯЗАНА учитывать различия двух рынков: разные торговые календари, часовые пояса и праздники; валюты CAD и USD; historical FX; symbol mapping; dual-listed securities; разные источники corporate actions; различия ликвидности; разные tick sizes; разные режимы исполнения; point-in-time sector membership; делистинги; смены тикеров. Каждое из этих различий — потенциальный источник рассогласования данных и подлежит явной политике на уровне поля или датасета.

## 8. Неизменяемость исходных данных

```text
Raw data is immutable.
Corrections create a new dataset version.
```

Исправление данных не редактирует исходный ряд, а порождает новую версию датасета с новым манифестом. Это обеспечивает воспроизводимость: любой прошлый backtest ссылается на конкретную версию данных и остаётся воспроизводимым после исправлений (`REQ-VALIDATION-002` и требования воспроизводимости в `33_Non_Functional_Requirements`).
